# WRO 2026 — Architecture & Criteria

## Platform constraints (the rules everything else follows)

- **Hardware**: Matrix Mini R4 — Arduino UNO R4 WiFi + STM32 co-processor
- **Language**: C++ via Arduino IDE
- **Memory**: limited. No `new` / `malloc` in steady state. No `std::vector`, `std::map`. Use fixed-size arrays.
- **Execution**: single-threaded `setup()` + `loop()`. No `delay()` blocking inside any `update()` path. All long-running work uses `millis()` comparisons + state machines.
- **Style**: module-based (`.h` / `.cpp` pairs or header-only). Global singletons exposed via `extern`. No class hierarchies for system structure.
- **Pathfinding lives off-board.** Dijkstra runs in Python (`tools/path_planner/`) and emits `routes.h` / `routes.cpp` as constant tables; the firmware does table lookups, not graph search.

## Dependency graph

Calls go top-down only. Lower layers never call upper layers. EventTrace is a side-channel observer — it polls public read-only state on other modules; nobody calls into it except via `pushEvent()`.

`cooperativeTick()` order (from `WRO2026.ino`):
`LineArray → Drive → LineFollower → Intersection → Manipulator → Tasks → PathTracker → Localization → Mission → EventTrace`.

The lower-layer modules tick first so that PathTracker / Mission see fresh state in the same loop iteration.

`Localization` sits BELOW `PathTracker` in the layering: PathTracker pushes its hop
activity DOWN each tick via `Localization.setNavActive(...)`, and `Localization.update()`
reads `Drive`'s encoders (also a lower layer) to integrate the operator offset. Both are
one-directional, downward dependencies — Localization never calls up into PathTracker.
It ticks AFTER PathTracker so the nav-active flag reflects the FSM's final state for the tick.

`Localization` also stores a 2D operator-offset delta (`Offset2D {x, y, thetaDeg}`)
accumulated between node arrivals — written only through its own methods, preserving the
ADR-005 single-writer rule (see ADR-042).

`reanchorAtWall(axis, coord, heading)` is a third pose writer alongside `zeroHeadingFromCurrent`
and `declarePosition`: at a wall-zero reset node it re-zeros the chosen position axis to the wall
coordinate AND squares the IMU-yaw offset, in one atomic call (see ADR-043). It still routes
through a `Localization` method, so the single-writer rule holds — the write set grows, the
writer module does not.

## The two iron rules

### Rule 1 — Everything that takes time has `update()`. Nothing blocks an `update()` path.

Every module that performs ongoing work exposes a non-blocking `update()` method. The main loop's `cooperativeTick()` calls each one in turn. If you need to "wait 100 ms," store a `millis()` timestamp and check elapsed time on each `update()` call.

The only `delay()` / blocking sites permitted in the codebase are command-time orchestration — `Drive::_drainBlocking()` (sync-default builders), `Drive::calibrateMotorBias()`, `WROLineArray::calibrate()`, and `Vision::readMosaic()`. These run from `setup()` or top-level operator actions (i.e., task bodies after `Drive.isIdle()`), never from a cooperative tick. Each blocking site spins the registered tick callback so OLED/heartbeat/sensors keep running during the wait.

### Rule 2 — Global singletons via `extern`

```cpp
// Drive.h
class DriveClass { ... };
extern DriveClass Drive;

// Drive.cpp
DriveClass Drive;
```

No `new` for system objects. No passing `Drive&` into every constructor. One instance per module, exposed via `extern`, used directly.

## Where PID lives (and where it doesn't)

| PID loop | Implementation |
|---|---|
| Motor speed → PWM | **STM32 firmware (vendor).** Not ours. |
| Motor position → speed | **STM32 firmware (vendor).** Not ours. |
| Sync mode (left vs right encoder match) | STM32 firmware (`MoveSync`). Gains in `Config::SYNC_PID_*`. |
| Gyro mode (yaw lock during straights) | **App code**, in `Drive::_emitGyroHold` (per-tick PD, ADR-072). Gains in `Config::GYRO_HOLD_KP` / `GYRO_HOLD_KD`. |
| Turn (IMU yaw → wheel diff) | **App code**, in `Drive::_updateTurnProfile` (per-tick PD, ADR-068). Gains in `Config::TURN_KP` / `TURN_KD`, plus the `TURN_CREEP_PWM` / `TURN_BREAKAWAY_PWM` / `TURN_SLEW_PWM_PER_TICK` floors. |
| Line offset → wheel-speed difference | **App code**, in `LineFollower::update()`. |

When `Drive.setSpeed(L, R)` is called, the STM32 ensures the wheels actually hit those speeds. The application's job is to compute *what* those speeds should be.

## Out of scope (this iteration)

- SD card storage
- Replay tooling (record/playback against the sim)
- Bluetooth / WiFi telemetry
- Sensor fusion beyond IMU sanity checks against expected heading

(Note: lightweight logging *is* in scope — see `EventTrace`, which renders the most recent four events on the OLED and emits a 500 ms Serial heartbeat. Anything heavier — SD logging, replay — remains deferred.)

## Coding criteria checklist

When writing or reviewing any module, confirm:

- [ ] No `delay()` calls inside `update()` paths
- [ ] No dynamic allocation after `setup()` finishes
- [ ] Module compiles standalone (only depends on layers strictly below it)
- [ ] State stored in module-private static or in the module's singleton instance
- [ ] No reads/writes to `Localization`'s current node from anywhere except `Localization` itself (via `onIntersection` / `onDeadReckonedAdvance` hooks)
- [ ] All public methods are either pure queries (`isDone()`, `getError()`) or one-shot commands (`start()`, `setSpeed()`); no method does both
- [ ] Loop iteration count or time bound is provable for any internal `for`/`while`
- [ ] Verbs with 3+ knobs use the fluent builder pattern; 0–2 knobs use direct calls (see [DECISIONS.md](./DECISIONS.md))
- [ ] Continuous primitives (`setSpeed`, `setSpeedSync`, `stop`) bypass the Drive queue; bounded/profiled moves go through it
